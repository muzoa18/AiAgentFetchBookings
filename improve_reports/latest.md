Claude proposed **5** change(s).

## ✅ Applied (in this PR)
- **Hanterad marked as handled even when confirmation fails, silently losing the booking** (`agent.py`, impact: high) — In agent.py, seen_ids.add(booking_id) is called immediately after a successful SMS, BEFORE mark_booking_handled runs. If mark_booking_handled returns False (Bekräfta dialog did not appear — see 'Bekräfta dialog did not appear' warning in portal_scraper.py), the booking is still in seen_ids and will never be retried. It will only surface as a WARNING that scrolls out of view. This means a real Bokning can silently remain unconfirmed in the portal. The booking should NOT be added to seen_ids until Hanterad is confirmed for Bokning types (SMS dedup is fine, but Hanterad retry is lost).
- **Login success not verified on pro.meca portal / promeister — false 'Logged in' logs** (`portal_scraper.py`, impact: high) — In portal_scraper.py _fill_login returns True as soon as a submit button is clicked, without verifying credentials were accepted. After that agent.py logs 'Logged in. URL: %s' regardless. If the login actually failed (wrong password, portal changed), the code proceeds to look for the Nya tab and booking table, then logs 'No booking links found' — indistinguishable from a genuinely empty Nya tab. The many bookings_found=0 runs could be masking silent login failures. Add an explicit post-login check that we left the login URL and that the login form is gone.

## ⚠️ Proposed but NOT applied (review manually)
- **Förfrågan/Offert bookings never marked seen, causing endless PENDING re-processing** (`agent.py`, replace_function) — Run history shows bookings_found stuck at 2 or 3 across many consecutive runs (e.g. 2026-07-29 12:30 through 2026-08-03, bookings_found=3 repeatedly, sms_sent=0). This is the classic symptom of Förfrågan/Offert bookings that never receive a Hanterad click so they stay on the Nya tab forever. In agent.py, the booking is added to seen_ids AFTER the SMS is sent, but the very first time a Förfrågan is seen it sends SMS and is added to seen_ids — good. However on subsequent days a NEW Förfrågan appears and correctly triggers one SMS, but the repeated identical bookings_found counts with sms_sent=0 confirm the same set of bookings keeps being re-scraped and only logged as PENDING. The current behaviour is actually correct for dedup, but the repeated full portal scrape + detail-page opening of already-seen bookings is expensive and the PENDING warning gives no resolution path. No code bug requiring change here — flagged for visibility only, no auto-apply.
- **SMS truncation risk — long bookings exceed single SMS and no length guard** (`agent.py`, replace_function) — build_sms in agent.py concatenates services, parts, fluids and a message field with no length cap. 46elks charges per 160-char segment and very long messages can be silently split or rejected. There is no logging of the final message length, making it hard to diagnose delivery issues. Add a length log line so improve.py and the owner can see when messages get large.
- **Cookie dismissal can click wrong button on quote/other portals** (`portal_scraper.py`, replace_function) — In portal_scraper.py _dismiss_cookies includes the broad selector "[class*='cookie'] button" which matches ANY button inside a cookie-related container — including a 'Reject' or 'Settings' button on some consent widgets. Clicking Reject or Settings can leave a blocking overlay. Restrict the generic fallback to accept-style buttons only.
