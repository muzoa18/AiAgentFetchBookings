- **Booking agent finds 0 bookings on every run for 3+ weeks** (`portal_scraper.py`, impact: medium) — Every run since 2026-09-24 reports bookings_found=0. Either the trigger gate (should_run) always returns False, or the Nya tab click / BookingInfo link collection is broken. The run history shows no 'skipped': true entries, meaning fetch_bookings() is actually running and returning empty — pointing to the Nya tab JS click or _collect_booking_links failing silently. The Nya tab regex /^Nya\b/ with text.length < 15 may no longer match the portal's current tab label (e.g. 'Nya 3' is fine but a renamed/localised tab or icon-only tab would fail). We cannot confirm without screenshots, so add diagnostic logging of the actual tab candidates to the Nya click step so the next run reveals why nothing is found.
- **No screenshot/page dump when Nya tab click fails but table exists** (`portal_scraper.py`, impact: low) — In fetch_bookings, when no booking links are found a screenshot is taken, but if the Nya tab click returns 'not found' the code proceeds anyway and only logs 500 chars of body text. Given 3 weeks of 0 bookings, we need the raw anchor count for ALL links (not just BookingInfo) to diagnose whether the detail-link href pattern changed. Add an all-anchor diagnostic dump when BookingInfo anchors are zero.
- **Trigger gate may silently suppress all runs in email mode** (`agent.py`, impact: high) — agent.py calls should_run(config) from email_trigger. If trigger.mode is 'email' and the Gmail query matches nothing (or OAuth fails), should_run returns False and the agent exits before ever scraping. The run history contains NO entries with 'skipped': true, which suggests either mode is 'always' (default) and the gate is passing, OR log_run is never reached because should_run raised. Wrap should_run in a try/except so a broken trigger never silently blocks booking processing, and log the trigger mode explicitly.
- **Login success is never verified — silent failure yields 0 bookings** (`portal_scraper.py`, impact: high) — In fetch_bookings, after _fill_login the code waits for a URL change but swallows PWTimeout with 'pass'. If login actually failed (wrong credentials, extra captcha, changed selectors), the code continues to the booking page which would be a login redirect, find no table/links, and report 0 bookings — exactly the symptom seen for 3 weeks. Add an explicit post-login check that the login form is gone and screenshot if still present.
- **run_logger does not capture scraping errors into run history** (`agent.py`, impact: low) — When fetch_bookings hits an exception it logs and returns [], and agent.py then logs bookings_found=0 with no error field. improve.py reads run_history.jsonl but cannot distinguish 'genuinely no new bookings' from 'scrape crashed'. Add an optional error marker so the structured history is diagnostic. This is why 3 weeks of zeros are ambiguous.
